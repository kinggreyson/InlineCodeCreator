# Contributing to Inline Code Creator

First of all thank you for looking at the project and considering becoming a contributor yourself! Inline Code Creator is a notes-first desktop application where runnable Python code cells live alongside formatted notes. This page will tell you how to get started and how changes get in.

## Start Reading here

1. **Read the README and the design doc.** The README summarizes what the project is and its purpose, and [docs/design.md](docs/design.md) explains how its built.
2. **Get your workflow setup.** Follow [docs/setup.md](setup.md). This document will experience ongoing changes as the project continues to progress. 
3. **Pick and Issue.** Comment on it to claim it.
4. **Open a pull request.** when you have something to show or update. It doesn't have to be finished since we are continually iterating on the project.

## Picking Work

- **Browse the [issues](../../issues).** There you will find bugs or new places to begin working. They will be labeled with Milestones and we are striving to complete earlier milestones first and fix those bugs first.
- **Claim it by commenting on it.** To avoid having multiple people doing the same work. If the work does go quiet for an extended period of time this issue may be claimed by someone else.
- **Have an idea for the project?** Open an issue first and describe the idea and the problem it would solve for the project. We need to agree on the need for the idea before taking the time to write the solution. Along with this we ask that you check the non-goals in the design doc before adding big ideas to the issues tab.

## Making a Change

These rules come from our [git standards](docs/git-standards.md). The reasoning for each is in that file.
### Summarized Policies
- **Branch** from an up-to-date main.
- **Commit Messages** follow the seven rules found in the git-standards. Subject under 50 characters, a blank line, then a body explaining why the change is needed.
- **Keep pull requests light.** One logical change, that is reviewable.
- **Describe the change.**  In your pull request: describe the problem, your approach, and what to look at first.

## Review Process

- A maintainer will review your pull request within 3 work days.
- Every change will require approval from someone who didn't write it.
- Review comments are just about the code, and you will have the chance to fix it, explain why it should stay the way it is, or open a new issue for it.
- Push those fixes as new commits on the same branch you are working on.
- We invite you to take a look at other people's pull requests and contribute in that way also.

## Merging

Maintainers merge approved pull requests, and the branch is deleted aftwerards. A change is finished when it is reviewed, merged, and working on 'main'.

## Questions

Please open an issue, or comment on an issue you are working on if you have any questions.
